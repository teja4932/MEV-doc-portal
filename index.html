M.Tech project · Amrita School of Computing

A smart-contract based framework for detecting MEV attacks

A prototype that watches live Ethereum pending transactions, applies eight behavioural rules to a rolling window and turns the result into an interpretable risk score from 0 to 100. The same rules are also written as a Solidity function.

Python monitorSolidity 0.8.24Foundry testsRule based, no machine learning

What it is

Maximal extractable value (MEV) is the profit that whoever orders transactions in a block can make by including, excluding or reordering them. Front-running, back-running and sandwich attacks are the common forms. This project looks at the pending transactions in the mempool and asks which of them show the patterns that such attacks usually leave.

Monitor

A Python program subscribes to pending transactions through a WebSocket provider and normalises each one into a fixed record.

Rules and score

Eight rules and a gas-anomaly check run on a rolling window. A flag weight, a scenario severity and a gas term are added into one score.

Contract

BlockAnalyzer expresses the same logic as a pure Solidity function that a caller can test with Foundry.

What it is not

Read this first These points are properties of the work and are repeated on the Scope and limits page.
  • The rules look for signals. A pending transaction is not a mined one, and a higher gas price is not proof of an attack.
  • No labelled evaluation was done, so no accuracy, precision or recall is claimed.
  • The Solidity contract does not read the mempool. Nothing connects the live monitor to it.
  • The monitor does not block or reorder anything. The advisory message is only a label.

Get running

Quick start

You need Python 3, a WebSocket endpoint of an Ethereum node provider, and optionally Foundry for the contract tests.

1. Set up the project

  1. Create a virtual environment in the project folder and activate it.
    terminal
    python -m venv .venv
.venv\Scripts\activate        # Windows
source .venv/bin/activate     # macOS / Linux
  2. Install the packages that the scripts import.
    terminal
    pip install websockets python-dotenv psutil matplotlib
    websockets and python-dotenv are used by the monitor. psutil and matplotlib are used by the benchmark script. The small helper scripts also use web3 and eth-abi.
  3. Add your provider endpoint to a .env file next to live_monitor.py. The monitor reads the variable ALCHEMY_WS_URL.
    .env
    ALCHEMY_WS_URL=wss://YOUR-PROVIDER-ENDPOINT/YOUR-KEY
    Keep the key privateDo not commit .env or put the key in a screenshot, a report or a repository. If a key was ever shared, create a new one in the provider dashboard and delete the old one.

2. Run the monitor

terminal
python live_monitor.py

The monitor subscribes to alchemy_pendingTransactions with full transaction objects. For every transaction it prints the rules that fired, the risk score, the level and the advisory message.

3. Reproduce the benchmark

live_performance_evaluation.py imports the monitor and runs four experiments of 100, 300, 500 and 1000 live transactions with the window set to 20. It writes the CSV files and plots into results_live/transactions_N/.

terminal
python live_performance_evaluation.py
FileContent
transaction_data.csvOne row per transaction: fields, signals fired, score, level, detection and end-to-end latency
detection_efficiency.csvMean, percentile and maximum time of each rule and of the scoring step
metrics.csvRun level numbers such as elapsed time and throughput
performance_graphs/*.pngThe plots shown on the Result plots page
Network traffic changesThe runs use whatever pending transactions arrive, so a new run gives different numbers. The recorded runs were made on 15 November 2026 between about 06:12 and 06:16 UTC.

4. Run the contract tests

terminal
cd foundry-project
forge test -vv --gas-report

test/BlockAnalyzer.t.sol has nine tests: one for each of the eight rules and one for a normal block. The compiler is set to 0.8.24 with the optimizer on and via_ir enabled in foundry.toml.

Test output not recordedThe pass or fail output of forge test was not captured in this work. Run it yourself and keep the output before you cite it.
Design

Architecture

One live path in Python and one separate, pure function in Solidity.

Data flow

The dashed box is not on the live path. Nothing in the project feeds the live stream into it.

Stages

1 · Input

The monitor asks the provider for pending transactions with full objects, not only hashes. Function: normalize_transaction.

2 · Normalisation

Hexadecimal quantities become integers. Value goes from wei to ETH and gas price from wei to gwei. A missing legacy gas price is skipped by R1, R6 and the gas-anomaly check.

3 · Rolling window

A deque with maxlen=20. The newest transaction is the last element and the oldest is dropped when the window is full.

4 · Rules and score

All rules run on every new transaction, whether or not they fire. calculate_risk_score combines their outputs.

Why a window of 20

The window bounds the work per transaction. Most rules read the window once, so their cost grows with its length. The sandwich rule tests ordered triples of positions, at most C(20,3) = 1,140 of them. The value 20 was a fixed design choice. No study of other window sizes was run.

Design

Detection rules

Eight rules and one extra check. Each returns true or false plus details used for reporting. The thresholds are constants in the code and none was calibrated on labelled data.

NumberingThis portal follows the numbering of the code and the thesis: R1 gas reordering … R8 sandwich. The journal paper uses a different numbering, so check the IDs before comparing the two.

Gas-anomaly check

Separate from R1–R8. With at least two positive gas prices in the window, it is true when the latest gas price is more than twice the mean positive gas price. It resembles R6 with a lower factor. It adds 10 points to the score but is not counted as one of the eight signals. Function: calculate_gas_anomaly / calculateGasAnomaly.

Four things to remember when reading a signal

Adjacent pairs only

R2, R3 and R5 read only the last two transactions. An attack with other transactions between its legs is not seen by them. R8 is the only rule that looks for a victim between two legs.

Calldata equality is a proxy

R5 and R8 compare raw calldata. They do not decode the token pair, the direction or the amount of a swap.

R7 uses ETH value

Many DEX swaps carry no ETH value, so R7 measures value concentration, not pool reserves or liquidity.

Gas price is not proof

R1, R2, R3 and R6 rest on gas-price differences, which are also caused by urgency. The results show how common they are in ordinary traffic.

Example: R1 in the code

def detect_gas_reordering(transactions):
    gas_prices = [
        tx["gas_price_gwei"] for tx in transactions
        if tx.get("gas_price_gwei") is not None
        and tx.get("gas_price_gwei") > 0
    ]
    if len(gas_prices) < 3:
        return False, None
    min_gas = min(gas_prices)
    max_gas = max(gas_prices)
    threshold = min_gas * 3
    if max_gas > threshold:
        return True, {"min_gas_gwei": min_gas, "max_gas_gwei": max_gas,
                      "threshold_gwei": threshold}
    return False, None
// Same rule in BlockAnalyzer.sol: checkReordering(Transaction[] memory txs)
// Zero gas prices are included in the sums on-chain; the function returns false
// when the minimum is zero (see the contract page for the differences).
Design

Risk scoring

One number from 0 to 100 that can be explained from its three parts.

Formula

S = min(100, w + s + a)

w  flag weight           10 if c ≤ 1,  20 if 2 ≤ c ≤ 3,  30 if c ≥ 4     (c = rules fired among R1–R8)
s  scenario severity     the first scenario that applies, tested in the order below
a  gas-anomaly term      10 if the gas-anomaly check is true, otherwise 0
Scenario (tested in order)s
R8 sandwich pattern40
R2 front-run25
R6 sudden insertion20
R1 gas reordering15
R3 back-run15
R4 repeated transaction10
R5 direction reversal10
R7 liquidity impact10
No rule fires0
LevelScoreMessage
LOWS ≤ 34[ALLOW]
MEDIUM35 ≤ S ≤ 69[MONITOR]
HIGHS ≥ 70[BLOCK]

The message is a text label that follows from the level. The monitor does not block or reorder anything.

Try it

Tick the rules that fire. The calculator follows calculate_risk_score in the Python monitor, including w = 10 when no rule fires.

10LOW
Rules fired (c)0
Flag weight (w)10
Scenario (s)Normal · 0

What the constants imply

  • The largest possible sum is 30 + 40 + 10 = 80, so the cap of 100 is never reached and scores 81 to 100 cannot occur.
  • Without R8 the largest score is 30 + 25 + 10 = 65, below 70. HIGH is reachable only when the sandwich rule fires.
  • When R8 fires, HIGH needs c ≥ 4, or c = 2–3 together with the gas anomaly. R8 alone with the gas anomaly gives 60, which is MEDIUM.
  • With no signal the Python monitor gives w = 10, so the lowest recorded score is 10. The Solidity function gives w = 0.
Recorded data agreeIn the 1,900 recorded transactions every score can be rebuilt as w + s + a. The highest score was 60, and no transaction reached HIGH because the sandwich rule never fired.
Design

The BlockAnalyzer contract

A Solidity 0.8.24 contract with one external pure function. It shows that the rules and the score can be written as on-chain logic and tested.

Interface

BlockAnalyzer.sol
struct Transaction {
    address from;  address to;
    uint256 value; uint256 gasPrice; uint256 gasLimit; uint256 nonce;
    bytes data;
}
struct ScenarioResult {
    bool isSuspicious; uint256 riskScore; string riskLevel;
    string scenario;  string recommendation; uint256 detectedSignals;
}
function analyzeBlock(Transaction[] memory txs)
    external pure returns (ScenarioResult memory);

Inside, there is one function per rule (checkReordering, checkFrontRun, checkBackRun, checkRepeatedTransactions, checkDirectionReversal, checkSuddenInsertion, checkLiquidityImpact, checkSandwich), plus calculateGasAnomaly, calculateFlagWeight, calculateScenarioSeverity, getRiskLevel and getRecommendation. An empty array returns a score of 0 with the scenario “Empty Block”.

What it does not doThe contract does not monitor the mempool, read blocks by itself, store detections, restrict addresses or block transactions. The caller must supply the transaction list. It is not a deployed on-chain defence.

Measured on 1,900 live pending transactions in four runs of 100, 300, 500 and 1,000 transactions, with the window set to 20. CPU and memory figures are left out on purpose.

Cost of each rule

Mean time per call, 1,000-transaction run

milliseconds, logarithmic axis

The sandwich rule takes 0.652 ms, about 91% of the summed per-component times, because it tests ordered triples. Every other component takes about 0.02 ms or less. A larger window would raise the cost sharply: a window of 40 has 9,880 triples, about 8.7 times the 1,140 of a window of 20. A window of 40 was not run.

Throughput and arrival

Throughput of each run

transactions per second

Throughput was 5.1 to 10.8 tx/s. It is limited by how fast transactions arrive, not by the analysis: 88 to 91% of the gaps between consecutive transactions were under 10 ms, and 9 to 12% were over 100 ms. Transactions arrive in bursts of about eight, and the analysis used well under 1% of the elapsed time.

How often the rules fire

Share of transactions on which each rule fired

percent of the transactions in the selected run
  • R1 gas reordering fires on 92 to 99.6% of transactions. A window of 20 pending transactions almost always contains a spread of more than three times in gas price.
  • R7 liquidity impact fires on 43 to 83%. Many pending transactions carry no ETH, and the rest are often unequal in value.
  • R2, R3, R4 and R6 fire occasionally. R5 is rare. R8 sandwich never fired.

What if the two frequent rules were removed

Computed offline from the recorded data, by recomputing the score without a rule. The share of MEDIUM transactions falls from 57.4% to 16.3% without R1, to 25.2% without R7, and to 13.4% without both. The mean score falls from 32.5 to 15.3. HIGH stays at zero. This shows how much of the MEDIUM level comes from two rules that fire on ordinary traffic.

Scope and limits

What the work shows, and what it does not.

Shows

The rules and the score can be implemented and run on a live stream at well under a millisecond per transaction on one machine.

The sandwich rule dominates the cost, and cost rises with window fill.

Gas-based rules fire on most ordinary pending traffic, so they separate little with the current thresholds.

Does not show

That the rules detect real attacks. No labelled data was used, so no accuracy, precision or recall exists.

That a flagged transaction was attacked, or that an unflagged one was safe.

That the result holds at other times, with other providers, or on other hardware.

Known limits

LimitConsequence
Pending is not minedThe order of pending transactions is not the order in which they are mined, so an observed order may not be the executed one.
Thresholds are not calibratedThe constants (3×, 2×, 30%, 50%) were fixed in the code, not chosen on data.
Calldata is not decodedR5 and R8 cannot see token pair, direction or amount, and an attacker who changes calldata is not matched by R8.
R7 is value basedIt does not use pool reserves, so it is not a liquidity model.
Two implementationsThe monitor and the contract differ in the points on the contract page, so they can score the same list differently.
Bursty arrivalThroughput reflects the arrival pattern of the stream, not the capacity of the analysis.
Short runsThe four runs took about four minutes in total, on one day.

Future work

  • Evaluate the rules against a labelled dataset of known MEV transactions.
  • Calibrate the thresholds and the score on data.
  • Decode swap calldata so the rules use token pair, direction and amount.
  • Compare pending transactions with the mined block and receipt.
  • Replace the triple loop in the sandwich rule by a grouped pass so that a larger window is affordable.
  • Repeat the runs at different times and with more than one provider.
  • Align the Python monitor and the Solidity function in the points where they differ.

Frequently asked questions

Is this machine learning?

No. Everything is fixed rules and fixed constants. There is no training and no learned weight.

What is the accuracy?

It was not measured. Measuring it needs a labelled dataset of attack and normal transactions, which this work did not use. The results show latency and how often rules fire, not how often they are right.

Why does the sandwich rule never fire?

R8 needs two transactions from one sender with identical non-empty calldata around a transaction from another sender, all inside a window of 20 pending transactions. That did not occur in the 1,900 recorded transactions. This is a result about this stream, not a proof that sandwiches do not occur.

Why is no transaction rated HIGH?

HIGH needs a score of 70, and without R8 the largest possible score is 65. Since R8 never fired, HIGH could not occur.

Why is R1 true for almost every transaction?

It needs only a maximum gas price above three times the minimum among three or more positive gas prices in the window. Pending traffic spans a wide range of gas prices, so this is usually true. It shows that the threshold does not separate much on this stream.

Can the contract protect users on-chain?

Not as it stands. It is a pure function that scores a list given to it. It cannot read the mempool or stop a transaction.

Why are CPU and memory not reported?

CPU was sampled once per transaction on a shared machine and is dominated by bursts of work, so it does not measure the cost of the method. The detection and end-to-end latencies are the reliable cost figures.

The paper and the portal use different rule numbers

Yes. The code and thesis order the rules R1 gas reordering to R8 sandwich. The journal paper numbers them differently, for example sandwich as R1. Compare rules by name when you move between documents.
